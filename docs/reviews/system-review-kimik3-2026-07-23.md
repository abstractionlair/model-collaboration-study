## Summary assessment

The design's intellectual core — macro-model framing, dollar-denominated compute matching, Best-of-N discipline, non-oracle aggregation, pre-registered fallback — is genuinely strong and the April review rounds visibly earned their keep. The most important issue is that the study's anchoring machinery has not caught up with the model market it studies: the Gemini truncation fix didn't just repair a harness bug, it invalidated the calibration, the best-subject anchor, and the cost structure the locked design is keyed to — and the codebase still contains the same defect class (silent truncation, task-hidden participants) at layers the April fixes didn't reach.

## Specific findings

Ordered roughly by severity. "Design" and "code" findings interleaved by importance rather than split by section (a)/(b).

**1. The aggregation layer never sees the task — the 2026-04-21 defect class, unfixed one layer down. (code, high)**
`_PICK_ONE_USER` (`src/experiment/prompts.py:173-178`) and `_SCORE_USER` (`prompts.py:167-170`) contain no `{query}`. The interpreter call sites pass only `candidates=` / `draft=` (`interpreter.py:603`, `:562`). Consequences per condition: B's judge picks among 8 code candidates without the problem statement; C's judge likewise; D/D′'s confidence scorer rates "confidence this answer is correct" without knowing what "correct" means. This is exactly the failure mode of the round-6 revise-prompt finding (`decisions.md` 2026-04-21: "hermetic sealing from ground truth should not be confused with hiding the task from participants"), present at the *selection* layer rather than the critique layer. It matters most for B: B is the load-bearing compute-matched baseline, and a judge that can only compare style/plausibility makes B weaker than the design intends, biasing the headline "beat B at matched dollars" comparison in favor of heterogeneous conditions. Fix before any confirmatory run: add `{query}` to both templates and both call sites (the answers' `production_query` is available, as the 2026-04-21 fix established), plus a smoke assertion that selection prompts contain the task. There is no selector-as-oracle argument against this — the task is not ground truth; the private tests are.

**2. Truncation is still silent across all three providers — the bug that just burned a calibration cycle is un-instrumented at the residual level. (code, high)**
No `finish_reason` / `stop_reason` check exists anywhere in `src/` (verified by search): `_call_openai` reads `choices[0].message.content` without checking `finish_reason == "length"` (`api_client.py:329`); `_call_anthropic` ignores `stop_reason == "max_tokens"` (`:287-301`); `_call_google` reads `response.text` without checking the candidate finish reason (`:402`). The 8x headroom fix removed the *common* Gemini case, but any call that exhausts its cap — on any provider — still produces a partial response that scores 0 with no marker distinguishing "model couldn't solve it" from "harness cut it off." The code comment at `api_client.py:381-382` claims this case is "documented rather than hidden"; it is not — there is no counter, no flag, no test (grep for `finish_reason` in `tests/` is empty). Suggested direction: a `truncated: bool` field on `CallRecord`, per-task truncation counters surfaced like the parse-failure counters, and a pinned policy (truncation = capability failure is defensible *if counted and visible*). The lesson of 2026-07-23 should be applied as a general rule: any harness-imposed bound that can silently corrupt a response needs telemetry.

**3. The study has no recalibration protocol, and the 2026-07-04 swap decision's recorded rationale is now known to be corrupted. (design/decision-log, high)**
The April calibration anchored `best_model=gpt-5.4-mini` on LCB. The pilot's A-columns (checkpoint, N=86) show gemini-3-flash-preview at 0.797 mean_frac vs gpt 0.523 / haiku 0.545. The design defines the baseline as "the best single subject model," so the current pilot's B/D′/C-judge/E-meta anchor (gpt) no longer satisfies the design's own definition — but the design contains no rule for when recalibration forces re-anchoring. Worse, `decisions.md` 2026-07-04 item 4 records the 2.5→3 swap rationale as "keeping 2.5-flash (noise, not signal, beyond easy)" — and `status.md` now establishes that 2.5-flash's April numbers were at least partly the truncation artifact (it also thinks by default). The swap may still be right, but its logged justification rests on data known to be corrupt; the decision log should say so explicitly, both for honesty and because the same artifact likely contaminated other April-era judgments. Suggested direction: pre-register a recalibration rule (re-run A-columns immediately before any confirmatory run; if the best subject changed, re-anchor and re-stratify; quarantine or disclose any tasks with observed condition-level outcomes).

**4. The `$X` anchor and tier structure are unstable under a cost-asymmetric pool, and the pilot has silently abandoned them. (design, high)**
The design anchors tiers to Condition A's cost on the best subject. Subject costs now differ ~20x per task (smoke run: gpt $0.0075, haiku $0.0076, Gemini $0.0702). With the gpt anchor, $4X = $0.030 — and *every* multi-model condition in the pilot exceeds it: B $0.050, C $0.084, D′ $0.038, E $0.125, D $0.258 (5x–34x $X). The `budget_tier: TWO_X` labels in the pilot logs are fictions; the runner doesn't enforce caps (documented in `runner.py:8-11`); compute-matching is actually being carried by the ad-hoc B-to-D′ realized-cost match. Matching B to each comparison's realized cost is arguably *stronger* than the tier structure, but it is a design amendment, not an implementation detail — it needs a `decisions.md` entry that says what supersedes what, before the confirmatory run inherits it by inertia. Note also that re-anchoring `best_model` to Gemini swings $X by ~9x, which swings every tier — the anchor's fragility is now an empirical property of the pool, not a hypothetical.

**5. The capability-gap-flatness assumption is broken, in both directions of re-stratification. (design, medium)**
`experimental-design.md` states Phase 1's capability gap is "mostly flat." On the checkpoint data: Gemini 0.939 medium / 0.736 hard; gpt 0.713 / 0.440; haiku 0.587 / 0.527. On the 16 tasks where Gemini scores ≤0.5 fraction, gpt sits at 0.198 and haiku at 0.298. So: keep the current pool and Gemini is in (above) the easy band; re-stratify to Gemini's band and the other two subjects fall toward the floor. Either way Phase 1 is now a gapped-pool experiment — which, notably, is the weak-overseer regime the project's motivation cares about — but the design text, the utility curve (+10pp middle assumed peer-like reviewers), and the power analysis all assume flatness. Whichever regime is chosen, say so and re-derive the assumed curve.

**6. Contamination-window asymmetry is unexamined for the new subject. (design, medium)**
LCB's contamination defense assumes subjects' training cutoffs roughly precede the release window. Gemini 3 Flash is a current-generation model evaluated on test6; its generation-jump score pattern (0.94 on medium where problems are most likely to have public solutions circulating) is also what contamination would produce. Gpt/haiku scoring 0.52/0.55 bounds the concern — the pool is not trivially solved by the other 2026-era models — but the write-up cannot claim contamination resistance for the Gemini columns without checking the temporal relationship between test6's contest window and the three subjects' cutoffs. One line of verification now beats one paragraph of hedging later.

**7. Abort taxonomy: three channels, three treatments, and the moderation-refusal class is unhandled. (code, medium)**
(a) `run_condition` catches exhausted `InfrastructureError` and scores it 0 (`runner.py:120-121, 142-147`) — but the design says infra failures are retried "from a later run window if necessary, until it completes cleanly" and *not* scored. (b) `ConditionResults.pass_rate` *excludes* aborted tasks (`runner.py:74`) while `run_pilot.summarise` *includes* them as 0 in the headline Mean frac (`run_pilot.py:227`) — two aggregate definitions in the same pipeline. (c) The pilot's one abort so far is an OpenAI content-policy 400 on `abc396_f` — a provider moderation refusal, surfaced as `unexpected_error` (the channel reserved for harness bugs) and scored 0. A moderation flag is neither a harness bug nor cleanly a capability failure; at N=400 the count will be non-trivial and vendor-asymmetric. Suggested direction: a third recorded category ("provider refusal"), pre-declared scoring treatment, and one aggregate rule used everywhere.

**8. The fractional-scoring statistical test and multiplicity policy are still unbuilt/unregistered after the fallback was adopted. (design, medium — pre-confirmatory gate)**
The 2026-07-04 decision adopted mean_fraction scoring and noted the binomial-GLM power analysis no longer matches the test ("test-case-level binomial or beta regression — kickoff work"). That work is not yet visible as done, and the multiplicity question across the ~10 protocol×tier comparisons (Bonferroni → N≈620/arm; FDR somewhere in 400–620) remains un-pre-registered. Both must land before the confirmatory run; both are cheap relative to a burned confirmatory cycle.

**9. Deterministic candidate order and reviewer pairing create systematic vendor-aligned biases. (code, minor)**
C's candidates are always in pool order (gpt=Candidate 1, haiku=2, gemini=3); any judge position bias becomes a per-vendor bias. D's cyclic reviewer assignment (`interpreter.py:316`) pairs reviewer→writer vendors identically on every task (haiku always reviews gpt, gemini reviews haiku, gpt reviews gemini). Any vendor-specific leniency is systematic rather than noise. Cheap fix: per-task seeded shuffles of candidate order and reviewer rotation. B is unaffected (homogeneous candidates).

**10. Google token split not recorded; visible-cap non-binding claim is currently unverifiable. (code, minor)**
`_call_google` sums `candidates_token_count + thoughts_token_count` into `output_tokens` (`api_client.py:409-412`). Billing-correct post-fix, but the split is the evidence for Q3's "visible output stays under the shared cap" claim and for reporting thinking-share as a finding. Record both components. Near-free.

**11. B-to-D′ match is approximate and the docstring disagrees with the practice. (code/process, minor)**
Smoke-run realized costs: B(n=8) $0.0497/task vs D′ $0.0379/task — B overspends by ~31%. Fine descriptively, but report realized ratios rather than calling it matched. And `run_pilot.py:16-19` still instructs matching B to *D's* realized cost while the launched run matched to D′ — the docstring drift is a symptom of the unresolved Q2 inside the repo itself.

**12. Pending-for-confirmatory items that are fine now but must not drift into the confirmatory run:** budget-cap enforcement (absent by design in `runner.py`); the 86 pilot tasks now have condition-level outcomes observed — if the re-stratified confirmatory pool overlaps them, re-selection must use A-column data only, and the overlap disclosed.

## Answers to the four posed questions

**1. Middle-band calibration invalid for the actual best subject.**

Fuse the first two options; reject the third as stated. Re-running harder-subset selection is not possible at current N: within test6 medium+hard, only ~5 tasks put Gemini in [0.3, 0.7] fraction and 16 at ≤0.5 — a Gemini-band subset of useful size does not exist in this pool. So the path is: execute the already-decided pool expansion (~5 releases toward N≈400), re-run the three A-columns with the fixed harness, re-anchor `best_model` to the empirical winner (the design's baseline definition *requires* this — it is not optional), select the band where that subject lands 0.45–0.55, re-run the power analysis at the observed base rate, then launch the confirmatory run. Cost is one calibration wave (~$35 at Gemini's realized $0.077/task × 400 + small change for the others). Note the regime consequence from finding 5: on Gemini's band the other subjects sit at ~0.2–0.3, so the heterogeneous conditions become weak-reviewer/strong-writer tests — declare that, since it changes the interpretation of a D win or loss and voids the flat-pool utility curve either way.

Option (c) — re-anchor to Gemini but keep the current pool — runs the confirmatory test with the anchor at 0.797 mean_frac, i.e., in (above) the easy band, while the fallback's power analysis assumed a 0.50 baseline and a +10pp effect. That is not the pre-registered test; it is a different test with the same name. What the current pool *is* good for is exactly what the pilot is doing: a descriptive easy-band datapoint (see Q4).

For the pre-registered fallback specifically: the rule is keyed to a power computation and the design's own strata mechanism is *selection* ("pick a subset where the best subject model lands in the target band"), so re-selection after recalibration is the pre-registered path — provided it happens once, is driven by A-column data only (the pilot's condition-level outcomes on these 86 tasks must not influence selection), lands before the confirmatory run, and is logged with the recalibration data. The fallback survives this; what would kill it is re-selecting after peeking at condition results on the same tasks.

Separately: amend `decisions.md` 2026-07-04 item 4's rationale — "2.5-flash is noise beyond easy" was measured through the truncation bug and is not evidence.

**2. B matched to D′ rather than D; is thinking spend compute?**

Matching B to D′ is sound for the D′ comparison and nothing else. The design's Best-of-N discipline is explicit: a multi-model result is valid only if it beats a *dollar-matched* B. D's realized cost is ~6.8x D′'s (smoke: $0.258 vs $0.038 per task), so B(n=8) at $0.050 under-baselines D by ~5x; a D-over-B "win" on this matching conflates structure with spend. For the confirmatory run, B needs per-comparison arms — at current prices B@D-cost is n≈40 gpt samples. (This folds into finding 4: realized-cost matching is a fine design amendment, but it must be made once, in writing, and applied to every comparison, not just the convenient one.)

On thinking tokens: yes, they are compute, and the design already settled the principle. Compute is operationalized as *billed USD* precisely because tokens don't compose across vendors and dollars are the binding real-world constraint. Thinking tokens are billed spend; excluding them would break dollar-composability and open a manipulation channel (any protocol could launder compute through a thinking-heavy vendor and claim efficiency). The right treatment is the one the design already invented for price arbitrage: a structural property of the pool that is *reported alongside results*, not matched away and not excluded. The 6x D-vs-D′ cost asymmetry belongs in the results table as a first-class descriptive finding. One caveat to keep honest: if best_model re-anchors to Gemini (Q1), D′ becomes Gemini-built and inherits the same thinking spend, at which point the D-vs-D′ comparison controls for it structurally — the asymmetry only bundles into the heterogeneity test while D′ is gpt-based.

**3. The 8x Gemini output budget: confound or acceptable asymmetry?**

Acceptable measured asymmetry — conditional on two things, one now true and one not. The equalization that matters for measurement validity is *visible-answer completeness*: every subject must be able to finish a full answer. OpenAI/Anthropic calls empirically use ~1.4–1.6k of their 4096 visible cap (non-binding); Gemini's thinking counts against its cap, so the shared 4096 truncated the answer (that was the bug). The 8x headroom restores completeness while the dollar meter records the true cost of Gemini's verbosity — and since matching is by dollars, within-call verbosity shows up in cost, where it belongs. This is the same policy-vs-number distinction the project already made for temperature on 2026-04-16: same *policy* (complete visible answer, vendor-default internal behavior, everything billed), not same number.

The two conditions: (a) billing must be complete — now true post-fix; (b) truncation must be *measured* — currently false (finding 2). A Gemini call that exhausts 32768 still truncates silently, and nothing in the harness would distinguish that 0 from a real failure — the same integrity hole, one level up. Add finish-reason telemetry and the candidates/thoughts split (finding 10), then this asymmetry is fully defensible. Also record the deviation in `decisions.md`: the design text still says "max_tokens pinned across providers," and the 8x happened without the kind of entry the temperature policy got.

**4. What would be overclaims in a public write-up of the pilot?**

Overclaims: (i) any "protocol X beats/outperforms the best single model" phrasing — the best subject sits at 0.80 on this pool (easy band for it), B's interim numbers are on a partial task subset that doesn't match A's completed subset, and N=86 single-seed CIs are wide; (ii) any compute-matched conclusion — caps unenforced, B matched to D′ not D, realized cost ratios unreported, tier labels fictional; (iii) any middle-band or strata-hypothesis claim — the pool is mid-band only for the April anchor; (iv) any C/D/E ranking; (v) any contamination-free attribution of Gemini's ability (finding 6); (vi) any "heterogeneity helps/hurts" claim — heterogeneity is currently bundled with a 0.25-point capability gap and a 20x cost range.

Safe claims: the harness findings themselves (thinking tokens count against `max_output_tokens`; they were unbilled; the fix moved Gemini from "unusable" to best-subject — a cautionary tale for anyone benchmarking thinking models); descriptive per-condition tables with CIs and explicit task-subset caveats; the D-vs-D′ cost-profile asymmetry; and — actually the most interesting artifact the pilot can produce — the calibration-erosion event as a methodological finding: a model generation released mid-study invalidated a three-month-old calibration and its downstream decisions, which is a real hazard of this research genre and worth naming as such. Frame the whole pilot as machinery validation plus an accidental easy-band descriptive datapoint, and nothing confirmatory.

## Recommendation

**Revise and re-review.** The design's core survives this round intact; nothing here warrants rethinking the approach. But the confirmatory run must not launch until: (a) the recalibration/re-anchoring protocol and the realized-cost-matching amendment are decided and logged (Q1/Q2/finding 4); (b) the aggregation prompts carry the task (finding 1) and truncation is instrumented (finding 2); (c) the fractional-scoring test and multiplicity policy are pre-registered (finding 8). The pilot should run to completion as the descriptive artifact it declares itself to be — its own framing is correct — and the write-up should stay inside the Q4 guardrails. The blocking items are targeted, not structural; this is the same shape as the April rounds' "revise" verdicts, and likely closable in a similar number of sessions.
