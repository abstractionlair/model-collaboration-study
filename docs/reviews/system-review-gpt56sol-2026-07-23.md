## Summary assessment

The conceptual design is unusually thoughtful: executable scoring, internal non-oracle aggregation, D′, and an explicit compute-matched baseline address several common weaknesses in collaboration studies. The current implementation and pilot do not yet realize the two load-bearing commitments, however: neither the dollar caps nor the corrected middle-band statistical design are operational, and several prompt, randomness, and evaluator issues can materially alter measured performance.

## Specific findings

1. **The budget tiers are currently labels, not enforced experimental constraints.** The design requires common dollar caps and says no multi-model result is valid without Condition B at the same tier (`docs/research/experimental-design.md:604-674`). The runner explicitly does not enforce caps (`src/experiment/runner.py:8-13`), while the pilot labels B/C/D/D′/E as `TWO_X` without calculating X or consulting the tier during execution (`scripts/run_pilot.py:136-187`, `scripts/run_pilot.py:412-418`). The Phase 1 builder also creates identical C/D/D′/E protocol trees at both 2X and 4X (`src/experiment/phase1.py:170-213`); absent cap-dependent adaptation, these are duplicate stochastic runs rather than different budget treatments. Matching B to D′ while D spends roughly six times as much leaves D without its load-bearing B comparator. Before confirmatory use, define X, choose the strongest B that fits each common cap, enforce or audit a predeclared overflow policy, and exclude or restructure any condition that cannot fit.

2. **“Middle band” is anchored inconsistently between calibration and the hypothesis test.** Task strata are defined by the best subject’s *one-shot* success, i.e. Condition A (`docs/research/experimental-design.md:495-508`), but the power analysis defines its 0.50 baseline as compute-matched Condition B (`docs/research/power-analysis.md:20-37`). B at 2X or 4X need not have A’s success rate and may be substantially stronger, so a pool calibrated to A≈0.50 can put the actual B comparator near ceiling. Resolve this before recalibration: either retain A-defined task difficulty and power the comparison using empirically estimated, tier-specific B rates, or define each tier’s middle band relative to B. The current assumed 0.50→0.60 comparison is not established by Condition-A calibration.

3. **The April calibration is invalid for the current experiment, and the proposed recalibration needs more than changing the model name.** It used Gemini 2.5 under a harness that truncated Gemini responses, whereas Phase 1 now uses Gemini 3 Flash with a corrected token budget (`docs/research/calibration-findings.md:22-36`; `docs/decisions.md:694-716`; `src/executor/api_client.py:368-413`). In addition, `scripts/run_calibration.py` makes one provider call per task; its `--seed` reaches only the interpreter, and Condition A has no interpreter randomness (`scripts/run_calibration.py:134-149`, `scripts/run_calibration.py:207-208`). It therefore does not estimate per-task one-shot probabilities or generation variance. Recalibrate all three subjects on the fixed harness and expanded, deduplicated pool with independent generation replicates, then validate the selected pool using held-out replicates or cross-fitting to limit regression-to-the-mean from difficulty selection.

4. **The existing N≈400 power result does not apply to the selected LCB outcome.** The calculation assumes independent binary outcomes and an unpaired two-proportion test (`docs/research/power-analysis.md:39-61`, `docs/research/power-analysis.md:105-121`), while the kickoff decision changed the outcome to task-level mean fractional test pass (`docs/decisions.md:708-712`; `src/experiment/benchmarks/livecodebench.py:338-364`). Conditions are also evaluated on the same tasks, private tests are clustered within tasks, and test counts vary. A test-case-level binomial model without task clustering would pseudoreplicate; it also changes the estimand by weighting tasks with more tests more heavily. Pre-register a paired task-level analysis—such as a hierarchical beta-binomial/mixed model or task-clustered paired analysis—define how 0/1 fractions and replicate runs are handled, settle multiplicity across protocols and tiers, and redo power from that model. Until then, “~400” is a useful scale estimate, not an established threshold.

5. **Several internal decision steps are task-blind.** PickOne in B/C receives candidate texts but not the original task (`src/experiment/prompts.py:172-178`; `src/executor/interpreter.py:592-606`). D/D′ confidence scorers likewise see only an answer (`src/experiment/prompts.py:166-170`; `src/executor/interpreter.py:547-563`). E’s peer critics use `PEERS_GROUPED`, which deliberately hides the task even though they are asked to assess correctness (`src/protocols/conditions.py:175-183`). This repeats the context-loss mechanism already found and fixed for D. On LCB, candidates are normally code-only, so the selector cannot reliably determine which program solves the requested problem. Include the production query in PickOne and ParScore prompts, and use task-visible review for E unless task hiding is an explicit ablation.

6. **The apparent seed control does not control model generation, and fallback randomness becomes position-biased across tasks.** None of the provider calls sends a generation seed (`src/executor/api_client.py:273-413`), so “variance across seeds” is not implemented; these are unlabelled provider-default replicates. Separately, each task constructs a fresh interpreter with the same seed (`src/experiment/runner.py:107-116`), which reconstructs `random.Random(seed)` (`src/executor/interpreter.py:101-124`). A parse failure or confidence tie therefore selects the same candidate position on every task in a run. Since candidate and cyclic reviewer order are also fixed, this can privilege one model or role. Use replicate IDs unless a provider seed is actually supported, derive deterministic task-specific fallback seeds or maintain a run-level RNG stream, and counterbalance candidate order and heterogeneous cyclic role assignments.

7. **The Google output-budget correction fixes truncation but currently violates the locked interface and lacks the telemetry needed to audit it.** Google receives 32,768 total output tokens while other providers receive 4,096 (`src/executor/api_client.py:368-386`), despite the design’s same-max-output requirement (`docs/research/experimental-design.md:703-728`). The implementation does not separately cap visible Gemini output to 4,096, record finish reason, or distinguish visible from reasoning tokens: `CallRecord.output_tokens` combines both (`src/executor/api_client.py:46-70`, `src/executor/api_client.py:402-413`). A nonempty truncated response is recorded as success (`src/executor/api_client.py:452-480`). Equal raw API parameters are not necessarily fair when one provider counts hidden thinking against the field, but the observable interface should still be equalized. Cap visible responses consistently, count all billed reasoning in dollars, and record visible tokens, reasoning tokens, finish reason, and truncation separately.

8. **LiveCodeBench candidate execution is not sandboxed and can access the oracle.** Generated code is run directly as the local user; only environment variables are scrubbed (`src/experiment/benchmarks/livecodebench.py:152-199`). No isolated working directory, filesystem restriction, network restriction, memory/process limit, or container boundary is present. Because decoded private tests live in the same readable workspace (`src/experiment/benchmarks/livecodebench.py:235-270`), candidate code can scan them and map hidden stdin to expected outputs; it can also damage files or consume system resources. Run every candidate in an ephemeral container or equivalent sandbox with no network, no benchmark files, a minimal read-only filesystem, and CPU/memory/process limits. This should block production execution independently of whether current models appear adversarial.

9. **Failure semantics disagree with both the design and each other.** The design says capability failures count as task failures while infrastructure failures remain unscored and are retried later (`docs/research/experimental-design.md:802-819`). The runner marks both as `aborted`, assigns both zero, but then excludes all aborted tasks from `ConditionResults.pass_rate` (`src/experiment/runner.py:72-77`, `src/experiment/runner.py:118-147`). The pilot summary instead leaves all aborted rows in its denominator (`scripts/run_pilot.py:214-233`). Thus capability failures can inflate the library aggregate, while infrastructure failures can depress the pilot aggregate. Use distinct typed statuses: capability failure equals a scored zero; exhausted infrastructure failure remains missing and queued for rerun; unexpected harness errors invalidate or halt the affected batch.

10. **The checkpoint and result records are insufficiently immutable for a long, resumable experiment.** Resume trusts whatever rows are in the checkpoint and never compares its stored metadata with current arguments or code (`scripts/run_pilot.py:369-396`). Changing seed, prompts, pricing, output policy, data, or code can silently mix old and new rows. The final record omits pricing values, prompt hashes, git commit, data digest, SDK versions, client configuration, per-call records, final responses, finish reasons, and reasoning-token decomposition (`scripts/run_pilot.py:445-459`). This is especially important after a harness bug changed results by nearly a full score range. Add a content-addressed run manifest and refuse incompatible resume; retain auditable per-call and final-response records with secrets excluded.

11. **The headline efficiency metric remains undefined for fractional scoring.** The design calls dollars per solved task the headline metric while LCB’s primary score is mean fraction (`docs/research/experimental-design.md:753-793`). “Solved” could mean strict all-tests-pass or fractional solved-task equivalents; those produce different rankings. The pilot currently reports dollars per attempted task, not dollars per solved task (`scripts/run_pilot.py:219-233`). Predeclare both a primary cost per unit fractional score and a secondary cost per strict full solve, or explicitly choose one.

12. **Model and role claims need narrower wording than the current research question may invite.** Gemini uses a mutable preview alias, despite the design’s preference for pinned versions (`src/experiment/phase1.py:53-60`; `docs/research/experimental-design.md:724-728`). D/E also use one fixed directed cyclic assignment, so their result identifies that concrete macro-model and ordering, not heterogeneous collaboration generally. Capture resolved provider model versions where possible, rotate roles in planned replicates, and reserve broad structural claims for effects stable across those rotations.

## Answers to the four posed questions

1. **Recalibration:** Treat the current N=86 run as an exploratory post-fix pilot and do not retrofit it into the confirmatory middle-band study. For Phase 1, expand the pool, deduplicate it, rerun all three Condition-A subjects under the fixed harness with multiple independent replicates, identify the actual best subject, and select/validate a harder pool against that subject. Harder-subset selection and pool expansion are complementary, not competing options.

   - Re-selecting only within the current 86 can produce a useful second pilot, but it cannot provide the required N and risks selection overfit. It preserves the fallback only if an independent validation replicate confirms the best subject is in-band.
   - Expanding and re-stratifying is the best route to preserving the predeclared fallback, subject to a new fractional-outcome power analysis and clarification of A-versus-B band anchoring.
   - Re-anchoring `best_model` to Gemini while accepting its ≈0.90 pool is necessary for honest B/D′/E construction but does **not** preserve the middle-band fallback. That pool is an easy/ceiling pool for the strongest constituent; results may be reported exploratorily as such, but not as the pre-registered middle-band test.

2. **B matching and thinking spend:** Matching B to D′ is sound only for an explicitly descriptive B-versus-D′ comparison. It does not supply the compute-matched baseline required for D. For a valid D claim, D and the strongest feasible B must share a declared dollar cap; D and D′ must likewise be evaluated under a common cap. Cap semantics permit unequal realized spend if both conditions fit, but the current pilot has not defined or enforced such a cap.

   Vendor thinking spend is compute under this project’s locked operationalization because it is billed API inference. Excluding it would reward hidden computation and contradict the dollar-based rationale. It is simultaneously a vendor behavior worth reporting: separate visible, reasoning, and input tokens and describe the D/D′ cost difference as part of heterogeneous deployment under market prices. A counterfactual analysis excluding or equalizing thinking may be useful as a secondary ablation, not as the primary matched-compute result.

3. **Output-budget asymmetry:** The current implementation is not acceptable as the final common interface, but restoring the same raw numeric API parameter would reproduce the truncation artifact. Equalize the delivered visible-answer cap and the dollar cap, not necessarily the provider field: allow enough Gemini total budget for hidden thinking, cap or validate its visible response at the same 4,096-token limit, and count every billed thinking token. Record finish reasons and both token components. Under those controls, provider-native hidden reasoning is an acceptable measured model property; without them, the 8× setting is an uncontrolled capability and cost asymmetry. A thinking-disabled or tightly limited Gemini sensitivity run would help distinguish lineage diversity from built-in inference-mode differences.

4. **Permissible pilot claims:** Safe claims are that the full matrix can run end-to-end on this particular LCB test6 pool, that a serious Gemini truncation/accounting bug was discovered, and that the exact run produced specified descriptive scores, costs, latency, and failure telemetry.

   It would be an overclaim to say that heterogeneous collaboration outperforms the best single model, beats a compute-matched baseline, isolates a heterogeneity effect, validates the middle-band hypothesis, establishes Gemini as the stable best subject, demonstrates reliability across seeds, generalizes beyond the three models and test6 stdin tasks, or provides evidence of no effect from a null comparison. It would also be misleading to describe N=86 as the pre-registered Phase 1 test: the pool is no longer middle-band for the apparent best subject, the analysis model is unsettled, only one uncontrolled provider replicate is present, and D lacks its matched B comparator. Even the nominal ~400 requirement should be described as provisional until fractional, paired, clustered power is recomputed.

## Recommendation

**Revise and re-review.** Let the running pilot finish as an exploratory engineering artifact, but do not use it for confirmatory or matched-compute claims. Before Phase 1, resolve the A-versus-B middle-band definition, redo calibration and fractional-outcome power, implement real dollar-cap discipline and manifests, repair task-blind internal prompts and randomness, separate reasoning telemetry, and sandbox executable scoring.
