# Review: Phase 1 Operational-Readiness Fixes

**Reviewer:** Codex / GPT-5.4
**Date:** 2026-04-17
**Artifact reviewed:** System at `master` commit `2b98c49` (fixes from commits `10a2f5b` and `2b98c49`), with updated `docs/research/experimental-design.md`, `docs/decisions.md`, `docs/status.md`, and new tests under `tests/`

## Summary assessment
Most of the round-2 operational blockers were fixed for real, not cosmetically. The API reliability, failure accounting, temperature-policy change, calibration gates, tracing updates, and new tests all materially improve the system. I still recommend **Revise and re-review** because the parser layer is not fully resolved: `_parse_score` and `_parse_pick` still confidently return wrong values on plausible response shapes, which means the measurement-quality problem has been narrowed but not closed.

## Specific findings
1. **The parser fixes are materially better, but they are not yet robust enough to call resolved.** In [src/executor/interpreter.py](/home/claude/projects/model-collaboration-study/src/executor/interpreter.py:552), `_parse_score` takes the last float in `[0,1]` before trying the `N out of 10` fallback. That still misparses realistic responses that echo the scale and then give a 10-point score, e.g. `"On a scale of 0.0-1.0, I'd rate this 7 out of 10"` currently parses as `0.0`, and `"On a scale of 0.0 to 1.0, I'd rate this 7 out of 10"` parses as `1.0`, not `0.7`. `_parse_pick` in [src/executor/interpreter.py](/home/claude/projects/model-collaboration-study/src/executor/interpreter.py:600) has the same remaining weakness in another form: `"I pick 2 because 3 is incomplete"` parses as candidate 3 because the fallback rule prefers the last in-range integer. The new tests in [tests/test_parsers.py](/home/claude/projects/model-collaboration-study/tests/test_parsers.py:21) cover the happy path and the old silent-fallback bug, but they do not cover these ambiguous mixed-number cases. I would tighten the heuristics and, where the response remains ambiguous, prefer `None` over a confidently wrong parse.
2. **The API reliability and observability fixes do resolve the earlier blocker set.** The Google retry narrowing in [src/executor/api_client.py](/home/claude/projects/model-collaboration-study/src/executor/api_client.py:127) is the right cut: 408/429, 5xx, and transport errors are retryable; other 4xx are not. The new `CallRecord.status` and `CapabilityFailure` handling in [src/executor/api_client.py](/home/claude/projects/model-collaboration-study/src/executor/api_client.py:394) cleanly separate success, capability failure, and infra failure, and they do it in the design-faithful way: empty/whitespace responses bill tokens and count as capability failures, while exhausted infra retries are recorded diagnostically but not charged against the macro-model budget. The tests in [tests/test_api_client.py](/home/claude/projects/model-collaboration-study/tests/test_api_client.py:29) are well targeted and I think these fixes hold.
3. **The calibration-gate changes are also substantive and close the specific placeholder footgun I flagged.** Requiring explicit `best_model`, `n_samples_for_b`, and `pricing` in [src/experiment/phase1.py](/home/claude/projects/model-collaboration-study/src/experiment/phase1.py:90) removes the previous silent path through `_best_model()`, `_n_samples_for_b()`, and implicit pricing. Renaming the convenience table to `PHASE1_PRICING_DRAFT` is also the right signal. There is still a deliberate runner-level gap: `base_cost_x` may remain `None` and a caller may explicitly pass draft pricing. I do not consider that a builder bug anymore; it is a runner-start enforcement problem and should be handled there.
4. **The temperature-policy change is a good correction, but it should be treated as an empirical calibration gate, not as something proven by design.** I agree with the decision in [docs/decisions.md](/home/claude/projects/model-collaboration-study/docs/decisions.md:445) and the implementation in [src/executor/api_client.py](/home/claude/projects/model-collaboration-study/src/executor/api_client.py:163): `temperature=None` with vendor defaults is a better same-policy interpretation than forcing `0` across providers. That does address the specific mode-collapse failure mode Gemini pointed out. But it does not guarantee that every vendor default is sufficiently stochastic for homogeneous B/D' conditions. I would keep the current policy, but I would treat “homogeneous pools still show meaningful output variance under vendor default” as something calibration should verify, not assume.
5. **The current client-layer shape is sufficient for later cost rollup; I would not add a cost API to `ApiClient` yet.** The combination of `CallRecord` token counts plus explicit `PricingTable` is the right substrate. The missing piece is run attribution, not per-call accounting. The runner should either instantiate a fresh client per run or snapshot `len(client.calls)` at run boundaries; both are cleaner than forcing run state into `ApiClient` itself. I do not see a client-layer change that is needed before the runner exists.

## Recommendation
Revise and re-review. Most of the round-2 blocker set is now genuinely resolved, but the parser layer still has realistic wrong-answer paths that can silently distort scoring and selection. I would fix that class of ambiguity, extend the parser tests to cover the mixed-number cases above, and then I would expect a `Proceed` recommendation to be justified.
